# fastapi-templates-xtn 中文架构总览

本文帮助维护者和下载使用者快速理解各模块如何配合，不替代英文详细规范。
实现或修改具体功能时，仍以 `SKILL.md` 路由到的英文 reference 和随附测试为
唯一详细执行标准；不要把本文复制成第二套独立规范。

## 适用范围

这是一个单项目 FastAPI 后端基线，核心范围是：

- PostgreSQL 用户、角色和权限；
- 用户名和密码认证；
- 五种固定图形验证码；
- Redis 固定窗口限流；
- JWT Access Token 加 Redis 活跃 JTI；
- 统一响应、结构化运行日志和分层审计。

它只服务一个项目和一套授权边界，也不默认加入第二套 Token 刷新凭据、
PostgreSQL Token/会话表、邮箱或短信验证码、MFA、匿名忘记密码、在线超级
管理员交接、全站共享限流、国家表或代理检测。

## 一次请求如何通过系统

普通受保护请求依次经过：

```text
解析并限制 Bearer Token 大小
-> 校验 JWT 签名、固定 claims 和时间
-> Redis 确认该 JTI 仍然活跃
-> PostgreSQL 读取当前用户、token_version 和完整角色权限
-> 校验账号状态、精确权限、严格管理层级和资源可见性
-> 执行业务
-> 返回统一响应，并写一条请求完成日志
```

登录和公开注册的顺序不同，但同样是失败关闭：

```text
可信来源 IP 和该业务的固定窗口限流
-> 校验并一次性消费对应图形验证码
-> 密码校验或注册事务
-> 仅登录成功时签发 JWT 并登记 Redis 活跃 JTI
```

无效、随机、过期或用途错误的验证码也已经消耗登录或注册额度；限流先拒绝
时不消费验证码，也不执行密码哈希、数据库写入或 Token 签发。

## 账号和密码

新项目默认只使用 `user_name` 和密码。用户名强制去掉首尾空白，只允许
3 到 32 位 ASCII 英文字母、数字或下划线，并拒绝固定敏感名称。删除账号
使用软删除，原用户名永久保留，不分配给另一个人。用户名是否区分大小写是
生成具体项目时集中询问的一项产品决定。

密码哈希直接保存在 `users`，不额外创建凭据表。使用 Argon2id，默认建议
8 到 60 个字符；是否分别强制大写、小写、数字和特殊字符由项目决定。基础
规则只额外拒绝整串顺序、整串同一字符和与用户名完全相同的密码。

公开注册默认开启，但最终以 PostgreSQL 中的持久开关为准；只有当前
`super_admin` 能修改。公开注册和管理员新增用户都只能绑定最低级 `user`
角色，客户端不能指定初始角色。

基础 Skill 没有匿名“忘记密码”接口。忘记密码时由有权限的管理员核实身份
并设置临时密码；用户再用它完成一次正式密码设置。临时密码不按时间过期，
但成功完成、再次重置或账号删除后立即失效。唯一 `super_admin` 的恢复在
可信主机线下完成。

## 五种图形验证码

新项目固定要求以下五种用途，不能跨用途复用：

| 用途 | 保护的操作 | 绑定主体 |
| --- | --- | --- |
| `login` | 用户名密码登录 | 可信来源 IP |
| `register` | 公开注册 | 可信来源 IP |
| `admin_create` | 管理员新增用户 | 当前登录用户 ID |
| `admin_reset` | 管理员重置下级用户密码 | 当前登录用户 ID |
| `self_change` | 本人修改密码 | 当前登录用户 ID |

每张图五分钟有效，只允许提交一次；答案正确、错误、用途错误或用户绑定错误
都必须原子删除该验证码。领取和刷新共用相应用途额度，默认每个主体
10 次/5 分钟。邮箱验证码、短信验证码和 MFA 只有项目明确提出时才另行设计。

## JWT 和登录会话

默认 JWT 只包含 `sub`、`jti`、`iat`、`exp`、`token_type`。`sub` 是不可变
用户 ID，不是用户名；默认有效期一小时，生成项目时必须提醒使用者按业务
风险调整。`iss` 和 `aud` 只有使用者了解作用并明确同意后才成对加入。

签名正确还不够。每个新 JTI 必须先登记到 Redis，后续请求也必须命中内容
完全匹配的活跃记录。退出当前登录会删除该 JTI；改密、管理员重置、禁用
账号或管理员强制下线通过增加 `users.token_version` 让该账号旧 Token 失效。

Redis 另外维护有效登录的 JTI 和登录时间，用于显示在线会话数量并在达到
项目选定上限时原子淘汰最早登录。这里记录的是登录会话，不代表物理设备。
普通用户只能退出当前登录；只有有权限的管理员才能强制退出严格低级用户的
全部登录。系统只签发 Access Token；过期后重新登录，不增加 PostgreSQL
Token 或会话表。

## 角色和权限

系统角色固定为：

| 角色 | 等级 | 主要边界 |
| --- | ---: | --- |
| `super_admin` | 1000 | 唯一持有人；系统角色与权限结构不可在线修改 |
| `admin` | 500 | 只能管理严格低于自己的用户和自定义角色 |
| `user` | 0 | 每个正常用户必须持有；没有权限管理能力 |

一个用户最多有 10 个未解绑角色。多个角色的权限取并集、管理等级取最高值。
系统只使用明确的正向 `resource:action` 权限，不默认加入 deny、通配符、角色
继承或独立委派系统。

权限通过并不等于可以操作任何目标。普通管理员不能查看或修改自己、同级、
更高级或受保护用户，也不能授予自己没有的权限，不能直接或间接给自己提权。
隐藏目标与不存在目标使用相同的 `404` 行为，列表的行和总数也必须使用同一
可见性条件。

首位 `super_admin` 不是第一位注册者自动获得。目标用户先正常注册为
`user`，再由开发或运维人员使用不可变用户 ID，在可信环境运行随附 PostgreSQL
脚本完成绑定。以后交接同样使用线下受保护脚本，没有在线交接接口。

## 原子一致性和软删除

权限写入先锁定唯一 `rbac_state(scope='global')` 行，再按固定顺序锁定用户、
角色和关系，重新读取当前权限后才决定是否写入。业务变更、版本号和必须的
审计成功事件在一个 PostgreSQL 事务中提交；任一失败则全部回滚。Redis 和
外部 HTTP 不放进这个事务。

用户、自定义角色、业务实体以及角色/权限绑定关系的运行时删除使用软删除。
解绑关系保留旧 episode，再次绑定创建新 ID。审计表只追加，不能软删除；
`rbac_state` 是固定控制行，也不能删除。

## 限流

限流使用 Redis Lua 固定窗口，每个业务和主体只有自己的计数键，没有全站、
全用户或跨业务共享额度：

- 未登录认证入口：固定业务加可信来源 IP；
- 已登录接口：固定业务加服务端认证的当前用户 ID；
- 不使用请求体里的用户名、邮箱或目标用户作为匿名限流主体。

基线默认值包括：登录 20 次/5 分钟、注册 5 次/小时、临时密码完成
20 次/5 分钟、每种验证码领取/刷新 10 次/5 分钟；已登录普通查询
600 次/分钟、普通写入 120 次/分钟、管理查询 300 次/分钟、管理变更
60 次/分钟。具体项目生成时要集中展示这些参数和修改位置，让使用者确认或
调整。Redis 无法可信判断时返回 `503`，不能静默放行。

## 响应、日志和审计

所有 API 使用真实 HTTP 状态和统一四字段 JSON：`code`、`message`、`data`、
`request_id`。`code` 是数字业务码；`request_id` 由服务端生成，并在响应头、
响应体和运行日志中一致。

运行日志是输出到 stdout 的单行结构化 JSON，用来排查请求、依赖、耗时和
未捕获异常。它不是审计记录，不能包含密码、Token、JTI、验证码答案、完整
请求体、数据库/Redis URL 或代理凭据。

审计分三类：

- `rbac_audit_events`：角色、权限、用户状态等访问控制决定；
- `account_security_audit_events`：注册、改密、密码重置等账号安全事件；
- `business_audit_events`：资金、所有权、重要状态、删除/恢复、人工覆盖、
  敏感导出或合规明确要求的业务事件。

`business_audit_events` 的表、模型、追加保护和安全写入工具属于随附基础
设施，但不会自动记录普通 CRUD。只有项目先确认动作目录、允许字段、结果和
保留策略后，对应业务调用点才写事件。基础设计没有审计投递 outbox、Worker、
租约、重试或死信系统。

## 主要 PostgreSQL 表

| 表 | 作用 |
| --- | --- |
| `users` | 用户名、密码哈希、账号状态、软删除、Token 和授权版本 |
| `roles` | 系统角色和自定义角色定义、等级、状态、版本和软删除 |
| `permissions` | 稳定权限目录 |
| `user_roles` | 用户角色绑定 episode、绑定信息和解绑墓碑 |
| `role_permissions` | 角色权限绑定 episode、绑定信息和解绑墓碑 |
| `rbac_state` | 唯一全局授权锁、授权 epoch 和公开注册开关 |
| `rbac_audit_events` | 只追加的权限管理审计 |
| `account_security_audit_events` | 只追加的账号安全审计 |
| `business_audit_events` | 可复用但仅按明确动作目录写入的业务审计 |

当前 `rbac_state` 只有三个非空字段：`scope`、`epoch`、
`public_registration_enabled`。验证码、限流计数和活跃 JTI 存在 Redis，
不为它们创建 PostgreSQL 表。

## 健康探针

`GET /health/live` 只说明进程还能响应，不读取数据库或 Redis。

`GET /health/ready` 用来决定部署是否可以接收流量。它在短超时内并发验证：

- PostgreSQL 的 `alembic_version` 只有一个版本，且必须为 `0004_password_auth`；
- 存在可读取的 `rbac_state(scope='global')` 固定行；
- 活跃 JTI Redis 和限流 Redis 都能执行 `PING`；
- 两套 Redis 都能执行 Lua `PSETEX`、`GET`、`DEL` 写读删探测。

Redis 探测使用随机的非敏感 Key，正常时在 Lua 内立即删除；异常中断时最多保留
五秒。成功返回统一 `200`，任一检查失败或超时返回统一 `503`。两种响应都带
`Cache-Control: no-store` 和服务端 `request_id`，正文不区分失败组件，也不包含
数据库名、连接地址、凭据、Redis Key、迁移版本或内部异常。内部日志只记录安全的
依赖分类和异常类型。

## 主要接口组

- 健康：`GET /health/live`、`GET /health/ready`；
- 公开认证：注册状态读取、图形验证码、注册、登录、临时密码完成；
- 当前用户：登录后验证码、本人改密、当前权限、会话列表、退出当前登录；
- 用户管理：列表、详情、新增、启用/禁用、密码重置、强制下线、绑定/解绑角色；
- 角色管理：列表、详情、创建、更新、启用/禁用、软删除、绑定/解绑权限；
- 权限：列表和详情。

除明确列出的公开认证入口和不返回业务数据的健康探针外，普通业务查询、业务
修改和管理接口默认都必须登录。公开路径和 OpenAPI 不使用 `rbac` 名称，避免
把内部授权实现暴露成外部 API 设计。

## 按需扩展

国家目录和代理可用性检测只是在项目已经使用本 Skill 时可选择的扩展。普通
地区字段、代理 CRUD 或无权限系统的通用 FastAPI 项目不会自动加载或实现它们。
需要时分别读取 [国家目录](country-catalog.md) 或
[代理可用性检测](proxy-availability-detection.md)。

## 版本和验证边界

官方验证环境是 Python 3.12、PostgreSQL 17、Redis 7。其他版本可以由具体
项目自行验证，但不能描述为本 Skill 已验证。集成测试必须使用全新、空白、
可丢弃且明确隔离的 PostgreSQL 和 Redis 目标。

`v0.5.1` 不改变数据库结构，不需要新增 Alembic 迁移。`v0.5.0` 已发布的
`0001` 到 `0004` 属于不可变历史；以后任何表或种子变化必须新增向前迁移，
不得改写已发布迁移。
